# RFC-0000 — ICG Architecture Manifesto

**Status:** Living Document

**Version:** 1.0

---

# Что такое ICG

Internet Capability Graph (ICG) — это распределенная операционная система
для интеллектуальных вычислений.

ICG не является

- LLM;
- AI-агентом;
- IDE;
- фреймворком.

ICG является слоем оркестрации между намерением пользователя
и вычислительными возможностями Интернета.

---

# Почему появился ICG

Современные AI-агенты устроены одинаково.

```
User

↓

LLM

↓

Tools

↓

Result
```

Размер модели определяет возможности системы.

ICG полностью меняет эту парадигму.

---

# Основная гипотеза

Интернет уже содержит огромное количество вычислительных возможностей.

Они распределены между

- LLM;
- API;
- браузерами;
- CI;
- облаками;
- локальными машинами;
- GPU;
- людьми.

Проблема заключается не в отсутствии вычислений.

Проблема заключается в отсутствии универсального механизма их композиции.

---

# Capability First

ICG никогда не думает категориями инструментов.

Он думает категориями возможностей.

Неправильно

```
Использовать Gemini.
```

Правильно

```
Нужна способность reasoning.
```

Какой Provider ее реализует —
решает система.

---

# Everything is a Resource

В ICG всё является ресурсом.

```
CPU

GPU

Filesystem

Browser

Docker

Git

LLM

Human

API

Robot
```

Все ресурсы описываются одинаковыми принципами.

---

# Everything is a Capability

Любое действие —
это Capability.

```
Reasoning

Coding

Planning

Testing

Compilation

Translation

Vision

Speech
```

Capability не зависит от реализации.

---

# Everything is a Graph

ICG состоит из графов.

```
Capability Graph

Execution Graph

Knowledge Graph

Dependency Graph

Resource Graph
```

Граф является основной структурой данных проекта.

---

# Separation of Concerns

Каждый компонент имеет одну ответственность.

Planner

↓

строит план.

Engine

↓

исполняет план.

Policy

↓

принимает решения.

Executor

↓

исполняет Capability.

Memory

↓

хранит опыт.

Discovery

↓

расширяет Graph.

Никакой компонент не должен выполнять обязанности другого.

---

# Learning by Experience

ICG не обучается на датасетах.

ICG обучается на собственной работе.

Каждый запуск —

новый опыт.

Каждый опыт —

новое знание.

---

# Route over Model

Главная единица знания —

не модель.

Не Provider.

Не Tool.

Главная единица знания —

маршрут выполнения.

Например

```
Planning

↓

Gemini

↓

Coding

↓

Kimi

↓

Verification

↓

Pytest
```

Именно маршрут становится объектом обучения.

---

# Late Binding

Никакие решения
не принимаются заранее.

Planner

не знает Executor.

Executor

не знает Graph.

Policy

не знает Workspace.

Все связывается
только во время выполнения.

---

# Open World

ICG предполагает,
что Интернет постоянно меняется.

Появляются новые модели.

Исчезают старые API.

Меняются лимиты.

Graph обязан уметь
адаптироваться автоматически.

---

# Replace Everything

Любой компонент системы
можно заменить.

Planner

↓

любой.

Memory

↓

любая.

Policy

↓

любая.

Graph

↓

любой.

Engine —

не меняется.

---

# Zero Vendor Lock

ICG никогда
не зависит
от конкретной компании.

Google —

Provider.

OpenAI —

Provider.

Anthropic —

Provider.

Oracle —

Provider.

Никто из них
не является частью архитектуры.

---

# Fail Gracefully

Любой Provider
может исчезнуть.

Любой API
может перестать работать.

Архитектура обязана
оставаться работоспособной.

---

# Long-term Vision

Конечной целью ICG является создание распределенной операционной системы,
которая способна самостоятельно обнаруживать,
комбинировать,
оценивать
и использовать вычислительные возможности Интернета
для решения произвольных задач.

LLM являются лишь одним из типов ресурсов.

Они не являются центром архитектуры.

---

# Non-goals

ICG не пытается

- создать новую LLM;

- конкурировать с ChatGPT;

- заменить Linux;

- заменить Kubernetes.

ICG решает другую задачу —

оркестрацию распределенного интеллекта.

---

# Architecture Law

Во время разработки любого нового компонента
необходимо ответить на три вопроса.

1.

Является ли это Capability?

2.

Является ли это Resource?

3.

Не нарушает ли это разделение ответственности?

Если ответ на третий вопрос —

"да",

архитектуру необходимо изменить.
