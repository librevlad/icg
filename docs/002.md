# RFC-0002 — Contract

**Status:** Draft

**Version:** 0.1

Depends on:

- RFC-0001 Capability Graph

---

# Цель

Определить универсальный формат задачи.

Contract является единственным способом общения между всеми компонентами ICG.

Никакой компонент системы не должен принимать "сырой" пользовательский запрос.

Любая задача сначала преобразуется в Contract.

---

# Основная идея

Contract не является Prompt.

Contract не является запросом к LLM.

Contract представляет собой декларативное описание намерения.

Он отвечает на вопрос

> Что необходимо сделать

но никогда не отвечает

> Как это сделать.

---

# Принципы

Contract

- не зависит от Executor;

- не зависит от модели;

- не зависит от CLI;

- не зависит от языка программирования;

- может быть сериализован;

- может храниться в базе;

- может передаваться по сети.

---

# Структура

Минимальная структура MVP

```yaml
id:

task:

workspace:

requires:

constraints:

inputs:

outputs:

acceptance:
```

---

# Поля

## id

Уникальный идентификатор.

Например

```
ctr_8f42c1
```

---

## task

Описание задачи.

Например

```
Add logging to authentication middleware.
```

---

## workspace

Рабочее пространство.

Например

```
point
```

или

```
~/projects/point
```

---

## requires

Список Capability.

Например

```yaml
requires:

- reasoning

- coding

- verification
```

Engine не определяет Capability самостоятельно.

Они должны присутствовать в Contract.

---

## constraints

Ограничения.

Например

```yaml
constraints:

- no new dependencies

- python>=3.11

- preserve public api
```

Executor обязан соблюдать ограничения.

---

## inputs

Входные данные.

Например

```yaml
inputs:

files:

- auth.py

- middleware.py
```

или

```yaml
inputs:

branch: feature/auth
```

---

## outputs

Ожидаемые результаты.

Например

```yaml
outputs:

modified_files

patch

tests
```

---

## acceptance

Критерии успешного выполнения.

Например

```yaml
acceptance:

- pytest passes

- ruff passes

- no new warnings
```

ICG считает задачу завершенной только после выполнения всех критериев.

---

# Жизненный цикл

```
User

↓

Contract

↓

Execution

↓

Result
```

Contract никогда не изменяется.

Изменяется только его состояние.

---

# Contract State

Минимальный набор состояний

```
CREATED

RUNNING

FAILED

COMPLETED
```

Позже могут появиться

```
WAITING

RETRYING

CANCELLED

PARTIAL
```

---

# Неизменяемость

После создания Contract запрещается изменять

- task;

- requires;

- constraints.

Допускается изменение только служебной информации

например

```
status

timestamps

execution history
```

---

# Serialization

Contract обязан поддерживать сериализацию.

Минимально

```
YAML
```

В будущем

```
JSON

SQLite

Network Protocol

Message Queue
```

Все сериализаторы обязаны представлять один и тот же объект.

---

# Валидация

Перед выполнением Contract обязан пройти проверку.

Проверяются

- обязательные поля;

- существование Workspace;

- корректность Capability;

- корректность структуры.

Если Contract невалиден —

Execution запрещен.

---

# Ответственность

Contract ничего не знает

о

- Graph;

- Engine;

- Executor;

- Memory;

- Events.

Он является исключительно описанием задачи.

---

# Acceptance Criteria

RFC считается реализованным если

✓ существует класс Contract;

✓ Contract является неизменяемым после создания;

✓ Engine принимает только Contract;

✓ Executor принимает только Contract;

✓ пользовательский ввод преобразуется в Contract до начала выполнения;

✓ Contract может быть сериализован и восстановлен без потери информации.
