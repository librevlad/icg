# RFC-0006 — Execution Policy

**Status:** Draft

**Version:** 0.1

Depends on:

- RFC-0001 Capability Graph
- RFC-0002 Contract
- RFC-0003 Executor
- RFC-0004 Execution Engine

---

# Цель

Отделить логику выбора Executor
от Capability Graph.

Graph хранит знания.

Execution Policy принимает решения.

Это один из важнейших принципов архитектуры ICG.

---

# Проблема

Наивная реализация выглядит так

```
Capability

↓

Graph

↓

Первый Executor
```

или

```python
return executors[0]
```

Это означает,
что Graph начинает содержать бизнес-логику.

Со временем в нем появятся

- if

- score

- weights

- fallback

- retry

что превратит Graph
в огромный объект.

Этого необходимо избежать.

---

# Основной принцип

Graph отвечает

только за знания.

Execution Policy отвечает

только за выбор.

---

# Архитектура

```
Contract

↓

Capability

↓

Graph

↓

Execution Policy

↓

Executor
```

Graph не знает,
почему выбран именно этот Executor.

---

# Ответственность Graph

Graph умеет

```
найти все Executor,
поддерживающие Capability
```

Например

```
coding

↓

Gemini CLI

Claude Code

Kimi CLI
```

И всё.

---

# Ответственность Policy

Execution Policy получает

```
Capability

+

Candidate Executors
```

и выбирает один.

---

# Интерфейс

```python
class ExecutionPolicy:

    def select(
        self,
        capability: Capability,
        candidates: list[Executor],
        context: ExecutionContext
    ) -> Executor:
        ...
```

Engine ничего не знает
о конкретной реализации Policy.

---

# MVP

Для MVP реализуется

```
PriorityPolicy
```

Алгоритм

```
вернуть Executor
с наивысшим приоритетом
```

Без

- статистики;

- обучения;

- случайности.

---

# Приоритет

Каждый Executor
может объявить Priority.

Например

```
Gemini CLI

priority = 100
```

```
Claude Code

priority = 90
```

```
Groq

priority = 70
```

Policy выбирает
максимальный Priority.

---

# Почему Policy существует отдельно

Потому что позже
появятся совершенно другие алгоритмы.

Например

```
RandomPolicy

RoundRobinPolicy

FastestPolicy

CheapestPolicy

SuccessRatePolicy

RLPolicy

ExplorationPolicy
```

Engine не изменится.

Graph не изменится.

Изменится только Policy.

---

# RL Policy

Будущая реализация

может использовать

```
Capability

+

History

+

Metrics

↓

Expected Success
```

и выбирать
не самый сильный Executor,

а наиболее вероятный
для конкретной задачи.

---

# Exploration

Одной из будущих Policy
станет Exploration.

Например

```
90%

лучший Executor

10%

новый Executor
```

Так Graph сможет
самостоятельно изучать
новые возможности.

---

# Fallback

Policy также отвечает
за резервный маршрут.

Например

```
Primary

↓

Gemini CLI

Backup

↓

Claude Code
```

Engine не вычисляет
Fallback самостоятельно.

---

# Ограничения Contract

Policy может учитывать

```
constraints
```

Например

```
offline only
```

или

```
free only
```

или

```
no cloud
```

При этом Graph
остается неизменным.

---

# Что НЕ делает Policy

Policy запрещено

- выполнять Executor;

- изменять Workspace;

- обращаться к Git;

- вызывать subprocess;

- строить Prompt.

Она только выбирает.

---

# Будущее развитие

В следующих версиях
Policy сможет учитывать

```
Latency

Cost

Availability

Success Rate

Energy

Privacy

Token Budget

Current Load

Historical Performance
```

При этом интерфейс

```python
select(...)
```

не должен измениться.

---

# Acceptance Criteria

RFC считается реализованным если

✓ существует интерфейс ExecutionPolicy;

✓ Graph не содержит логики выбора;

✓ Engine использует Policy;

✓ MVP реализует PriorityPolicy;

✓ новую Policy можно добавить без изменения Engine;

✓ новую Policy можно добавить без изменения Graph;

✓ выбор Executor полностью инкапсулирован внутри Policy.
