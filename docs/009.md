# RFC-0009 — Planner

**Status:** Draft

**Version:** 0.1

Depends on:

- RFC-0002 Contract
- RFC-0007 Execution Graph

---

# Цель

Определить компонент,
который превращает намерение пользователя
в исполнимый Execution Graph.

Planner — единственный компонент системы,
который занимается декомпозицией задачи.

---

# Основная идея

Planner отвечает только на один вопрос:

> Какую последовательность действий необходимо выполнить,
> чтобы решить поставленную задачу?

Planner ничего не исполняет.

---

# Архитектура

```
User Task

↓

Contract

↓

Planner

↓

Execution Graph

↓

Execution Engine
```

Planner заканчивает работу
в момент построения DAG.

---

# Planner не является LLM

Planner —

логическая роль.

Он может использовать

- Gemini CLI;
- Claude Code;
- локальную модель;
- заранее заданные шаблоны;
- человека;
- внешний сервис.

Engine не знает,
каким образом был построен план.

---

# Ответственность

Planner обязан

- прочитать Contract;
- определить необходимые Capability;
- определить зависимости;
- построить Execution Graph.

Planner запрещено

- выполнять Executor;
- изменять Workspace;
- запускать команды;
- изменять Graph.

---

# Интерфейс

```python
class Planner:

    def plan(
        self,
        contract: Contract
    ) -> ExecutionGraph:
        ...
```

---

# Вход

Planner получает только Contract.

Например

```yaml
task:
    Add logging to authentication middleware.

workspace:
    point
```

---

# Выход

Planner возвращает DAG.

Например

```
Planning

↓

Locate Files

↓

Modify Code

↓

Run Tests
```

или

```
Planning

↓

Backend

Frontend

↓

Verification
```

---

# Planner не знает Executor

Planner работает
только с Capability.

Например

```
coding
```

а не

```
Gemini CLI
```

или

```
Claude Code
```

Выбор Executor
происходит значительно позже.

---

# Capability Selection

Planner определяет

какие Capability нужны.

Например

```
Task

↓

Need

coding

verification

git
```

Planner никогда
не выбирает исполнителя.

---

# Декомпозиция

Planner обязан
разбивать большие задачи.

Например

```
Implement OAuth
```

↓

```
Read Project

↓

Find Auth Layer

↓

Modify Backend

↓

Update Tests

↓

Verification
```

Размер одной вершины
должен быть минимальным.

---

# Granularity

Planner обязан
избегать

слишком крупных узлов.

Плохо

```
Write whole backend
```

Хорошо

```
Create endpoint

↓

Implement service

↓

Write tests
```

---

# Независимые ветви

Planner обязан
выделять независимые части.

Например

```
Planning

↓

Backend

Frontend

Documentation

↓

Verification
```

Это позволит
позже выполнять их параллельно.

---

# Ограничения

Planner обязан учитывать

Contract Constraints.

Например

```
offline only
```

или

```
no internet
```

или

```
python only
```

---

# Ошибки

Если Planner
не способен построить граф,

он возвращает ошибку.

Engine
не начинает выполнение.

---

# Planner ничего не знает

Planner запрещено знать

- Executor;
- Policy;
- Memory;
- Statistics;
- Success Rate.

Planner отвечает только
за структуру задачи.

---

# Planner Context

Planner может использовать

- структуру проекта;
- список файлов;
- README;
- архитектурные документы;
- предыдущие планы.

Но не имеет права
исполнять код.

---

# План как артефакт

Execution Graph
является полноценным артефактом.

Он может

- сохраняться;
- экспортироваться;
- анализироваться;
- переиспользоваться.

Это позволяет
нескольким Planner
генерировать планы
для одной задачи.

---

# Будущее развитие

Позже Planner сможет

- строить несколько альтернативных DAG;
- оценивать стоимость выполнения;
- учитывать исторические маршруты;
- повторно использовать успешные шаблоны;
- оптимизировать граф перед выполнением.

Но интерфейс

```python
plan(contract)
```

не должен измениться.

---

# Что НЕ входит

Planner ничего не знает

о

- LLM API;
- Gemini CLI;
- Claude Code;
- Bash;
- Docker;
- Git.

Все это появляется
только во время исполнения.

---

# Acceptance Criteria

RFC считается реализованным если

✓ существует интерфейс Planner;

✓ Planner принимает только Contract;

✓ Planner возвращает только ExecutionGraph;

✓ Planner работает исключительно с Capability;

✓ Planner не знает Executor;

✓ Planner не выполняет задачи;

✓ Engine получает готовый DAG и не занимается планированием.
